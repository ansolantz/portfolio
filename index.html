Specialist area

Design Systems

A recurring focus throughout my work has been turning design decisions into scalable, reusable frontend systems. I have led frontend Design System development, built Flutter component libraries and reference applications, and worked closely with designers in Figma to keep design and code aligned.

Design + code as one system

I work closely with designers from the component definition stage, translating Figma specifications into reusable Flutter APIs. Naming, component structure and tokens are intentionally aligned across Figma and code so designers and developers share the same language.

Reusable Flutter libraries

I have led frontend development of Design System libraries covering foundations, themes and reusable components across multiple applications. I focus on composition, predictable behaviour and APIs that are clear for product developers to understand and use correctly.

Reference app + documentation

The library is supported by a reference application where teams can explore components, variants and states in one place. I document components and APIs carefully so the system is useful beyond the team that originally built it.

Quality built into the system

I implemented golden testing around component demos to automatically detect visual regressions. Accessibility, interaction states, dark mode and cross-platform behaviour are treated as part of the component contract rather than product-by-product fixes.

How I work

From Figma specification to tested component.

Design tokens bridge visual decisions and implementation, including colour, typography, spacing, sizing and radius. Components are then built once, documented, demonstrated in the reference app and protected with automated visual tests before adoption in products.

Figma→Tokens→Flutter API→Reference app→Golden tests
One source of truth

Shared foundations and components reduce duplicated UI decisions and keep experiences consistent across products.

Faster product work

Teams can focus on feature-specific problems instead of repeatedly rebuilding and styling common UI.

Safer change

Centralised tokens, components and tests make system-wide changes easier to propagate and visual regressions easier to catch.

Case study 01

LiveWell by Zurich

Building a Design System from the ground up while contributing to a large health and wellbeing product.

RoleSenior Flutter Developer
FocusDesign System, product development
TechnologyFlutter, Dart, Riverpod
PlatformAndroid, iOS & web
· Context · My work · The system · Outcome

Creating a shared foundation

I built and evolved the LiveWell Design System from the ground up, working closely with design and product teams to establish a consistent visual and technical foundation. The work combined system thinking with hands-on product development, so the Design System had to work in real product flows rather than as an isolated component library.

From foundations to product adoption

Foundations

Defined color, typography, spacing, sizing, radius, icons and dark mode as reusable foundations.

Components

Built reusable Flutter components and tokens with well-structured APIs, clear conventions and maintainability in mind.

Accessibility

Incorporated accessibility into components and design standards instead of treating it as a later layer.

Adoption

Worked with product teams to replace legacy components and gradually move the app towards the new system.

Product work

Contributed directly to features while solving UX issues, technical debt and cross-squad implementation challenges.

Design System

Built to work in the real product.

Foundations, reusable components and patterns created a shared language between design and engineering, while supporting accessibility, theming and cross-platform consistency.

Product development

Hands-on feature development

Design System work alongside real product development.

Alongside the Design System, I worked directly on product features and user flows, including health and activity tracking and social sharing. Working on both the system and the product helped ensure that reusable components were shaped by real implementation needs.

I worked extensively with collecting and presenting health data from Apple Health, Google Fit and connected devices, turning complex datasets into intuitive and meaningful user experiences.

Outcome

A more consistent, accessible and scalable product experience.

The Design System made it easier for teams to build and maintain new features while moving the product toward higher reuse and consistency.

  • Increased reuse reduced development time by around 30%.
  • Closer alignment between Figma and implementation reduced repetitive design cleanup and improved designer satisfaction.
  • Shared foundations created a more consistent and professional product experience.
  • Replacing hundreds of custom UI elements with reusable components significantly reduced duplication and codebase size.

Product delivery

Built and improved health and wellbeing features, including activity-focused experiences and real user flows.

UX quality

Fixed visual and interaction inconsistencies and helped bring the implemented product closer to the intended Figma experience.

Technical quality

Replaced legacy UI, reduced duplicated code and improved maintainability while continuing to deliver product features.

Design collaboration

Worked closely with designers so product needs, component behaviour and implementation details informed each other.

From product to ecosystem

After LiveWell, I worked on the next step of the Design System approach within Zurich Global Ventures. The goal was to create a shared foundation that could be reused across multiple apps while still allowing each product to maintain its own identity.

The challenge shifted from creating consistency within one product to exploring how a Design System could support multiple products, teams and visual identities without losing the benefits of reuse.

Share what should be shared

Core building blocks and conventions reduce repeated effort across teams.

Keep products flexible

A shared system should enable product identity, not flatten every experience into the same UI.

Build for maintenance

Improvements to shared foundations can benefit multiple apps instead of being solved repeatedly.

Case study 04

Natural Machines

Designing and building the user experience for Foodini, a 3D food printer with its interface running directly on an integrated Android tablet.

RoleJavaScript / Flutter Developer
ProductFoodini 3D food printer
TechnologyReact, JavaScript, Flutter, Dart, Provider
PlatformIntegrated Android tablet

A very different kind of product interface

Foodini is a 3D food printer, which meant designing for an experience very different from a conventional mobile or desktop application. The interface had to make an unfamiliar physical process feel understandable and approachable on the machine's integrated touchscreen.

I worked initially with React and JavaScript, then helped build the next generation UI in Flutter as the product moved to a new cross-platform codebase.

Physical + digital

The UI was part of a real appliance, connecting software interactions with a physical printing process.

Make the unfamiliar clear

The experience needed to guide users through a new way of preparing food without making the technology feel complicated.

React to Flutter

The product gave me early hands-on experience moving an existing interface from React and JavaScript to Flutter.
