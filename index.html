Specialist area

Design Systems

A recurring focus throughout my work has been turning design decisions into scalable, reusable frontend systems. I have led frontend Design System development, built Flutter component libraries and reference applications, and worked closely with designers in Figma to keep design and code aligned.

01

Design + code as one system

I work closely with designers from the component definition stage, translating Figma specifications into reusable Flutter APIs. Naming, component structure and tokens are intentionally aligned across Figma and code so designers and developers share the same language.

02

Reusable Flutter libraries

I have led frontend development of Design System libraries covering foundations, themes and reusable components across multiple applications. I focus on composition, predictable behaviour and APIs that are clear for product developers to understand and use correctly.

03

Reference app + documentation

The library is supported by a reference application where teams can explore components, variants and states in one place. I document components and APIs carefully so the system is useful beyond the team that originally built it.

04

Quality built into the system

I implemented golden testing around component demos to automatically detect visual regressions. Accessibility, interaction states, dark mode and cross-platform behaviour are treated as part of the component contract rather than product-by-product fixes.

How I work

From Figma specification to tested component.

Design tokens bridge visual decisions and implementation, including colour, typography, spacing, sizing and radius. Components are then built once, documented, demonstrated in the reference app and protected with automated visual tests before adoption in products.

Figma→Tokens→Flutter API→Reference app→Golden tests
One source of truth

Shared foundations and components reduce duplicated UI decisions and keep experiences consistent across products.

Faster product work

Teams can focus on feature-specific problems instead of repeatedly rebuilding and styling common UI.

Safer change

Centralised tokens, components and tests make system-wide changes easier to propagate and visual regressions easier to catch.
